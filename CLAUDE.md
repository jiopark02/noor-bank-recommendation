# CLAUDE.md

## What belongs in this file (read this first)

This file is loaded into every session, so anything stale here becomes a wrong premise for every decision.

- **Record only what changes when the code changes**: conventions, invariants, file pointers, traps, principles, settled decisions.
- **Never record live state**: env var values, Supabase dashboard settings (auth providers, applied migrations, RLS state), DB rows, which deploy is serving, external approvals. They change without a commit and rot silently.
- **Never record counts or inventories.** They are derivable and rot; run `audit/L0-evidence.sh` and `audit/L0b-evidence.sh` instead.
- **Verify live state against the running system**, not against this file or source. Schema, constraints, indexes, RLS and policies are read in the Supabase SQL Editor. This repo carries no live-check SQL file; ask the operator for the ready-made queries.
- Line numbers drift; grep for the identifier. Priorities and the TODO list live in the operator's documents outside the repo; ask the operator what is next.

## Working Agreement (these rules override convenience)

**Language.** Code, comments, commit messages, SQL, migrations and team-facing documents: **English only**. Conversation with the operator may be Korean. Existing Korean comments are being migrated; don't add new ones.

**Hard environment constraints**
- **Local Node is not a build-verification path.** Sanctioned local uses: `tsc --noEmit`, `npm audit`, `npm ci`, `vitest run`. `npm run dev` / `npm run build` are not verification (the machine holds no secrets; `.env.local` is prohibited there). Never claim "verified" without a Vercel deploy. Run `npm ci` before trusting any local command.
- **Vercel and CI both gate a push.** Vercel type-checks source (tests excluded via tsconfig); `.github/workflows/test.yml` runs the tests on every push to main and every PR, installing with `npm ci`, so lockfile drift fails at install. Its test step is `npm run test --if-present`: a missing `test` script passes silently. Its `npm audit` job is `continue-on-error`. A failure from GitHub infrastructure (action download, runner acquisition) is not a code failure; re-run all jobs.
- **Verification loop.** After each change run the related tests and `node_modules/.bin/tsc --noEmit` (local binaries through `node_modules/.bin/`, never `npx`, which goes to the registry when the package is missing), redirecting raw output to a file in a temp directory outside the repo (redirect, don't pipe, so the exit code survives). Cite the file. The vitest suite lives in `src/lib/__tests__/`; look there for a test covering a module before changing it. The boundary probes `sharedDataReferences`, `plaidTokenPlaintextSites` and `chatSystemPromptSites` (helpers in `sourceProbe.ts`) keep a per-name allowlist, each entry with its reason, of the files that name the household sharing tables, `household_share_set` (the only function that inserts grants; `household_leave`, which only deletes them, is not tracked) or `household_shared_connections` (which returns the connections another member shares with a person), reach the decryption of a stored Plaid access token (the plaintext token at exchange is not tracked), or build a model's system message; a file that newly reaches one or stops reaching one fails until the allowlist changes, and a name passed through a variable is not seen.
- **No `Co-Authored-By` trailer.** Commits are authored solely by the operator.
- **Migrations are applied manually** in the Supabase SQL Editor, and SQL can reach the database without a migration file. Never assume a committed migration is live, or that one you did not run is not. If a design depends on schema, a live query is the gate.
- **The migrations directory is not the schema's source of truth.** The live database holds UNIQUE constraints no migration creates (`users.email`, `survey_responses.user_id`).
- **Vercel env changes (deletions included) need a manual redeploy.**
- **Single production deploy from `main`**, auto-built on push; the tech team pushes too. Run `git fetch --prune` right before creating a branch and right before a push or merge, not at session start. After pulling, re-check that earlier fixes survived.
- **PowerShell host:** commands handed to the operator avoid `&&` and `curl -H` (use `Invoke-RestMethod`). `vercel env ls` is unavailable; env vars are read in the Vercel dashboard.
- **`tsconfig` targets ES5** — beware `matchAll` and iterator spread.

## Architecture

### Auth & session
All auth goes through Supabase Auth.
- `src/lib/supabase-browser.ts` — browser singleton `supabase`, with a no-op Web Lock to avoid supabase-js's orphaned-lock hang. **Never call raw `getSession()`.** Use `readSession()` when the result decides anything, `getSessionSafe()` only where a missing session changes nothing but display.
  - `getSessionSafe()` returns `null` alike when the client is not configured, when there is genuinely no session, on the 3-second timeout, and on an error — thrown, or returned in `getSession()`'s own error field. `readSession()` keeps them apart: `none` is a clean no-session answer; `unavailable` is everything else, which a valid session can produce and which must never sign anyone out. The signed-in pages decide through `src/lib/sessionFlow.ts`: only `none` clears local auth state and goes to `/login`; `unavailable` shows a delay screen whose button reloads. Don't add callers that collapse these cases.
  - OAuth uses PKCE with `detectSessionInUrl`; supabase-js exchanges the code while the client initializes (no `exchangeCodeForSession` in `src/`), and a retry waits on the same memoized initialization, so a hung exchange recovers only through a full reload — hence the reload buttons. Re-check this behavior when upgrading auth-js.
  - Name collision: `src/lib/validation.ts` also exports an unrelated `getSession()` that reads a `SessionConfig` from localStorage or sessionStorage.
  - Signing this device out goes through `runSignOut` (`sessionFlow.ts`), and every `auth.signOut` states its scope. When the server call fails, `runSignOut` deletes this device's auth cookies directly. Signing the user's other devices out goes through `POST /api/account/sessions/sign-out-others` (`accountSessions.ts`), which passes the request's verified bearer token to the admin sign-out with scope `others` and clears nothing on this device.
  - "Keep me signed in" unchecked sets the `noor_session_only` cookie; while present, the browser client's and the middleware's cookie writers write auth cookies with no lifetime. `@supabase/ssr` overrides `cookieOptions.maxAge`, so lifetime can only be changed in the cookie writer.
- `src/lib/supabase.ts` — server side. `createServerClient()` **requires `SUPABASE_SERVICE_ROLE_KEY` and throws without it** (no anon fallback), so it always bypasses RLS; `createAdminClient()` likewise. `isSupabaseConfigured()` returning true does not mean the constructor succeeds. A missing key surfaces wherever the throw is caught: the `apiAuth.ts` helpers turn it into null, and a caller that answers null with 401/403 reports the fault as an auth failure.

**RLS is a backstop, not the primary defense.** The explicit `.eq('user_id', ...)` filter is the first line, and the id must come from the verified token, never a request body. Grep before assuming a route is covered. Deliberate exceptions: `getPlaidConnectionsByItemIdAcrossUsers` (`plaidApiUtils.ts`) reads by `item_id` only, for signature-verified Plaid webhooks, taking the owner from the row; and `household_shared_connections` (below, under households) returns another person's connection rows, deciding by share grant and membership in SQL, called with the verified caller's id only.

API routes that act for a user verify identity through `src/lib/apiAuth.ts`: `resolveRequestAuth()` checks the bearer token, directly or through `getAuthenticatedUserIdFromRequest()` and the route gates built on them. Admin routes also call `requireAdmin()` (service-role-only `admin_users`); it is fail-closed, but **the caller must `return 403` on null** or the route fails open. Exception: `/api/plaid/webhook` has no Supabase auth; its only gate is the `Plaid-Verification` check (`plaidWebhookVerification.ts`), which runs before the body is acted on.

**Profile rows are written by the application, not by a trigger.** A `public.users` row is created by the email signup route and upserted by `src/app/api/auth/sync-profile/route.ts` after every sign-in; the profile sync also ensures the one-person household. An Auth user created any other way has no profile row until one of them runs.

`src/middleware.ts` gates **pages, not API routes** (the matcher excludes `api/`, so API rate limiting cannot live there). It redirects to `/login` when a `PROTECTED_PREFIXES` path has no session. It checks session presence only: the `/admin` pages have no role check of their own (the `admin/*` API routes do). The app creates no anonymous sessions (`signInAnonymously()` has no call site). It returns a response from several paths — the demo-host redirect, the public passthrough, a 503 (`Cache-Control: no-store`) when the Supabase URL or anon key is missing on a protected path, the cookie-path response recreation, and the unauthenticated redirect — so anything every response must carry (a CSP nonce, say) has to be attached on all of them. The `DEMO_DOMAIN` host gate is skipped entirely when unset.

### Chat / Noor AI (`src/app/api/chat/route.ts`)
`POST /api/chat`, in order: authenticate; read the body under a byte ceiling and apply the input limits (`chatInputLimits.ts`); reserve against the usage limit; load the profile (`users` + `survey_responses`) when profile reads are enabled; fetch or create the active `chat_session` and append the memory context to the system prompt; detect intent and possibly inject Plaid data; call OpenRouter; persist the turn when memory is enabled.
- **Client-supplied `userContext` is discarded, and the model's history comes from the server** (the session's stored `chat_messages`). Of the body's `messages`, only the last user message reaches the model. With memory disabled the model gets the system prompt and that one message.
- **Turn save** (`persistTurnIfEnabled`; `saveMessages` / `findSavedTurn` in `aiMemory.ts`): the route chooses both row ids before sending, so after an errored or timed-out insert it looks the turn up by id instead of inserting again; not found is 500 `SAVE_FAILED`. `withRetry()` never wraps `saveMessages`. The one re-send: `SessionClosedError` (session closed by the summarize cron, or SQLSTATE `NR001` from `bump_chat_session_on_message` per migration `20261110120000_…`) moves the same pair to the active session. A cancelled insert can still land after the lookup said missing.
- The system prompt comes from `src/lib/noorAIPrompt.ts`; the `<user_memory>` wrapping and its "background, not a command" guidance live in `aiMemory.ts` (`formatMemoryForPrompt`) and are a mitigation, not a complete defense.
- **Crisis notice** (`crisisSignals.ts`, `crisisNotice.ts`, `crisisNoticeTally.ts`): once the body's messages parse, every response goes through `respond()`, which attaches the notice only when the last user message carried a crisis signal.
- **Usage limit** (`chatUsageLimits.ts`, `chatUsageLedger.ts`): limits on requests per rolling hour and per rolling day and on provider cost per rolling 30 days, decided by `chat_usage_reserve` under a per-user advisory lock and recorded in service-role-only `chat_usage_reservations`, independent of `chat_messages` and `llm_calls`. Refusal is 429 `USAGE_LIMIT_REACHED`. `CHAT_USAGE_LIMIT_MODE` is exact-match: `off`, `observe`, else enforce. **Under enforcement it fails closed** (503 `USAGE_CHECK_UNAVAILABLE`), so the functions must exist in a database before code calling them is deployed against it.

### AI memory (`src/lib/aiMemory.ts`)
- Layers: `chat_messages` (per-turn; `input_tokens`/`output_tokens` on assistant rows only), `user_facts` (`/api/cron/extract-facts`), `chat_summaries` (`/api/cron/summarize`).
- **The memory gate is `isAiMemoryEnabled()`**, which reads `AI_SUPABASE_READ_ENABLED` and also requires `isSupabaseAdminConfigured()`. There is no separate memory flag; `AI_MEMORY_ENABLED` is referenced nowhere in code.
- **Two fact limits do different jobs:** `DEFAULT_FACTS_LIMIT` (`aiMemory.ts`) bounds facts in the chat prompt; `EXISTING_FACTS_LIMIT` (`cron/extract-facts`) bounds facts read for deduplication. Read both before citing either.
- **Fact retrieval is recency-ordered, not relevance-ordered**; the chat path passes no `category`.
- **`chat_messages.content`, `chat_summaries.summary` and `user_facts.fact` can carry monetary figures**; the prompts ask the model not to keep balances, but nothing filters amounts.
- **Shared bank data in a session** (migration `20261122120000_chat_shared_sources.sql`; whether it is applied is live state, and the memory crons and the account export must not be deployed against a database without it). A `chat_shared_sources` row records the earliest moment a connection another household member shares entered a chat session. A message of that session created before the moment is unaffected; every message created at or after it counts as carrying the shared figures, since the session's history returns to the model on each later turn. Both crons read that moment first (`getEarliestSharedSourceTime`) and then only the messages before it (`getSessionMessages` with `before`); a session with nothing before it is marked done without a model call, and a failed read of the moment throws before the model is called. Keep that order: when sharing ends, the rows marking the moment are deleted together with the messages they mark. The moment is a database timestamp string and is passed on unchanged, never through a `Date`.
- **Storing a turn that carried another member's data** (migration `20261124120000_chat_shared_turn_save.sql`; whether it is applied is live state). Its `chat_shared_turn_save` (SECURITY INVOKER, service_role only) replaces `chat_shared_source_record`, which that file drops: in one transaction it checks that the session is the caller's and open and that every (owner, connection) pair is still returned by `household_shared_connections`, then records each pair in `chat_shared_sources` and inserts both messages, writing one database moment to the mark and the user message (the assistant's is 100 ms later). It answers `saved`, `session_closed`, `not_shared` or `busy`, and every answer but `saved` means nothing was written. It waits only for its first advisory lock, while it holds nothing: every later lock (the other pairs' advisory locks, the session row, the caller's `users` row) is taken without waiting, and one held elsewhere answers `busy`, because the purge can hold a session row while it waits for another grant's lock, and account deletion holds the `users` row while its cascades wait for the sessions. Running `20261122120000_…` again after it recreates `chat_shared_source_record`; apply the turn-save file again. Nothing in `src/` calls either function yet (`chatSharedSourceRecordCallers.test.ts` holds that for the old one), and no code puts another member's data into a chat. The code that will do so has to: save through it every turn where the other member's data enters the prompt, with the pairs whose data entered (a turn that only received the data through the session's history included); when it answers `session_closed`, call it again for the new session with the same ids; and decide how a turn that needs none of the other member's data avoids continuing a marked session, because everything after the moment stays out of summaries and facts and is deleted when sharing ends.
- **Output filter** (`memoryOutputFilter.ts`): SSN-shaped strings and Luhn-valid card numbers are masked in summaries and refuse a fact (`SensitiveFactRejectedError`), as does a crisis signal in a fact. `chat_messages.content` is not filtered; account numbers are not matched.
- All functions use `createAdminClient()`; **every per-user query filters by `user_id`**. Only the cron maintenance scans cross users, and extraction trusts `chat_sessions.user_id` only.
- **Crons:** bounded LLM calls per run, per-call timeouts and a time budget (`llmTimeouts.ts`), input budgets (`cronInputBudget.ts`); leftovers are `deferred` to the next run.
- **Retry and give-up** (`memoryCronBatch.ts`, `cronRetryBound.ts`, columns from migration `20261111120000_add_cron_retry_state_to_chat_sessions.sql`, which must be applied before this code is deployed against a database). Only failures of the model's answer or a provider input rejection are counted; reaching the limit marks the session given up (`<p>_outcome = 'given_up'`). **`summarized` / `facts_extracted` = true means the cron is finished with the session, not that a summary or fact exists**; `<p>_outcome` tells given up from done. To re-queue given-up sessions after the fix is deployed, reset the flag and every `<p>_` state column together in one update so the row passes the pair check.

### Signup path (`src/app/api/survey/route.ts`, logic in `src/lib/emailSignup.ts`)
- Email signups are created **unconfirmed** through `auth.admin.generateLink({ type: "signup" })` (also used by `/api/auth/resend-confirmation`, `resendConfirmation.ts`). For an existing unconfirmed user it issues a new token (the old one dies) and **overwrites `user_metadata`**; a confirmed user gets `email_exists`. `auth.admin.createUser` and `signUp()` have no call site; the other entry point is `signInWithOAuth`.
- Invariants in `createEmailAccount`: look up `users` by email first (a failed read is 500, never "no row"); **the emailed token is always made after its send claim** succeeds; a resignup uses the stored row's names, never the request's; a non-23505 insert failure rolls the Auth user back; a survey insert failure still answers 200 with `surveySaved: false`.
- **The confirmation email is ours** (Resend, `sendSignupConfirmationEmail`). `buildConfirmationLink` puts the token in the URL **fragment**; `/auth/callback` verifies (`verifyOtp`) only on a button press and strips the fragment on read.
- **Send limit:** every send first claims through `email_confirmation_claim` (migration `20261104120000_email_confirmation_sends.sql`), which fails closed, so the migration must be live before this code is deployed.
- `buildSurveyRow` writes only the monthly money answers and the credit-history answer, with the fixed columns; every other body key is ignored, so the table's other columns are not written by the app.

### Plaid (`src/lib/plaid.ts`, `src/app/api/plaid/`)
- `PLAID_ENV` (default sandbox) is read in one place. Transactions only; US only; multiple connections per user by `item_id`. Plaid auth deletes `body.userId` before use.
- **`AI_PLAID_STATE`** (`resolvePlaidStateMode()`, `plaidChatContext.ts`): after trimming and lowercasing, anything but `connection` / `balances` is `off`. There is one fresh bank read into the chat prompt, `getPlaidChatState`, inside the capability-scaffold branch of the chat route; `off` denies that channel, so nothing is read. The balance-keyword channel reads nothing itself: under `connection` a balance question it allows raises that read's depth to `balances` (`resolvePlaidChatDepth`), and under `balances` it denies, since that mode already reads balances on every turn but a greeting. The financial-planning channel is denied unconditionally. **`off` does not reach bank figures already in stored history, summaries, facts or cron input.**
- `src/lib/plaidEgressPolicy.ts` (`evaluatePlaidEgressDecision`) is the single decision surface for Plaid data reaching the LLM; every channel in `PLAID_EGRESS_CHANNELS` must deny under `off`, which a test walks.
- **`plaid_connections.status` is unmaintained** (nothing writes it after insert), and the sealed bank-data block prints every row, errored ones included.
- **Revocation before row deletion, per connection.** `/api/plaid/disconnect`, `/api/account/delete` and the webhook's revocation call `itemRemove` and delete the row **only** on success; a failed revocation keeps the row (`plaidRevocation.ts`, `accountDeletion.ts`, both tested by execution). Account deletion tries every connection it has time for, revoking each it can, and stops before deleting the user while any is left un-revoked, so a partial run is normal. The only Plaid rejection treated as success is `ITEM_NOT_FOUND` / `ITEM_ERROR` for a token from the deployment's environment (sandbox-observed). A delete that matched nothing is a logged success; a delete with no representation is a failure that may or may not have removed the row. Where migration `20261121120000_household_share_grants.sql` is applied (live state), deleting the row also deletes its share grants and answers through their foreign keys. Where migration `20261122120000_chat_shared_sources.sql` is applied as well (live state), each grant deleted that way also deletes, in the same statement, the chat messages of the person it was shared with from the moment the connection's data entered their session; a failure there fails the row delete, which keeps the row.
- **Revocation time.** Every route that can reach a revocation exports a literal `maxDuration` equal to `PLAID_REVOKE_ROUTE_MAX_DURATION_SECONDS` (`plaidRevocation.ts`; `plaidRevokeRouteDuration.test.ts` holds them equal). The account-deletion loop checks the request's remaining time before each connection (`shouldStartRevocation`, `PLAID_REVOKE_START_RESERVE_MS`): with too little left, that connection and every later one are not started, are logged `deferred=time_budget`, and count in `remaining`, so the answer is `REVOKE_INCOMPLETE` and a retry continues. This only stops new revocations from starting; no call in the path is bounded in code, and `itemRemove` runs without a time limit on purpose.
- **Account deletion reads the connections again after revoking**, before it deletes the `users` row: a failed re-read is `CONNECTION_READ_FAILED`, a row still present (one stored by a concurrent request) is `REVOKE_INCOMPLETE`, and nothing is revoked at that step; a retry starts over from the first read.
- **Configuration gates on these routes.** `/api/plaid/disconnect`, `/api/plaid/relink`, `/api/plaid/exchange-token` and `/api/plaid/create-link-token` check `isSupabaseAdminConfigured()` before authenticating and answer 503 `ADMIN_UNCONFIGURED`, since without the gate a missing service-role key reads as a 401. The webhook answers 503, which Plaid retries, when the service-role key or the token encryption key is not configured, before it reads the row. Relink answers a failed connection read with 500 `CONNECTION_READ_FAILED` and keeps 404 for an absent row.
- **Why a bank-connection request was not authenticated.** `/api/plaid/exchange-token` and `/api/plaid/create-link-token` authenticate through `authenticateWithCause` and answer a refusal through `plaidAuthRefusal` (`plaidApiUtils.ts`): an auth server that gave no usable answer is 503 `AUTH_UNAVAILABLE`, every other cause stays 401, and each refusal logs one line, `[plaid-auth] route=… refused=…`, built from the route name and the cause only, so nothing from the request reaches it. `/api/plaid/disconnect` and `/api/plaid/relink` keep `authenticate()` and its plain 401; `GET /api/plaid/connections` has no body to read and calls `getAuthenticatedUserIdFromRequest()` directly, answering a null with the same plain 401 and without telling the causes apart.
- **The browser side of a new connection** (`plaidConnectFlow.ts`, `usePlaidExchange.ts`): both requests go out only with a session's access token, and Link's public token is held in memory only, until the exchange is known to have ended. An exchange whose outcome is unknown is not sent again unchecked: the connection list is read, and only an active `itemId` that was not in the screen's list when the token was received counts as connected. **`GET /api/plaid/connections` sends `itemId`, `institutionName`, `status` and `createdAt` per row and no institution id**, so nothing in the browser can match a row to a bank by one (`plaidConnectListContract.test.ts` runs the route to hold this).
- **Error logs from the `plaid_connections` helpers** (`plaidApiUtils.ts`) on these paths carry the error code only, through `postgrestErrorCode` (a code of an unexpected shape logs as `invalid`); `getAllPlaidConnections` still logs the error object.
- **`/api/plaid/exchange-token`** (`plaidExchange.ts`) revokes the Item it just minted when it refuses it after the exchange — never an Item this user already has a row for, and not at all when that ownership read fails. A failed save revokes only when nothing can have been stored; otherwise the row is re-read (one retry): a row is success, no row is revoke, and an unreadable row leaves the Item unrevoked with `revoke=skipped reason=recheck_read_failed`. An Item Plaid reports no institution id for (null, empty or blank) is never stored: it is revoked and answered 502 `INSTITUTION_ID_MISSING`, logged `refused=institution_id_missing source=plaid`, apart from `refused=item_get` where the lookup itself failed. A unique violation (23505) on the insert has two causes, so the user's row for the Item is read (one retry) before anything is decided: a row is success and no revocation; no row means another Item's active row at the same institution, so the new Item is revoked and the answer is the duplicate 409; an unreadable row leaves the Item unrevoked with `refused=store_conflict … revoke=skipped reason=recheck_read_failed`. A `compensate=failed` or `recheck_read_failed` line is the only record of that Item.
- `plaid_connections` is service-role-only (migration `20261013120000_…`). Do not add policies or client grants; browser needs go through an API route.
- Access tokens are stored **encrypted** in `plaid_connections`, only through `src/lib/plaidTokenCrypto.ts`, as `v<n>:<iv>:<authTag>:<ciphertext>`; one key version is live at a time. **The AAD is `<version>:<user_id>`, with the id of the row's owner taken verbatim**: for the caller's own rows, the verified token's id; for a connection shared with the caller, the owner id `household_shared_connections` returns with the row. A normalized id, or another person's, fails to decrypt, invisibly to `tsc` and unit tests. `readBankData` takes one id for every row it is given, so rows of two owners are never read in one call. **Every failure is fail-closed, with no plaintext fallback and no exception** (account deletion included). A row that will not decrypt is usually recoverable by restoring the key; deleting it makes its Item unrevokable forever.
- Duplicate detection runs in the application (pre- and post-exchange by institution id, `active` rows only), and `CONNECTION_LIMIT` counts every row. Migration `20261116120000_unique_active_institution_per_user_on_plaid_connections.sql` backs it with a partial unique index on `(user_id, institution_id)` whose condition must stay the same as that filter (`institution_id is not null and status = 'active'`); whether it is applied is live state. **The index must only exist on a database whose every writer tells the two causes of a 23505 apart.** So deploy the code that tells them apart before applying the index to the database it writes to, and to roll the code back to a version that reads every 23505 as the row for this Item, drop the index first: older code on a database with the index stops on an institution conflict without revoking the Item it just minted. Where the index is applied, a write that sets `status` back to `active` or changes `institution_id` can fail with 23505 too.

### Households, share grants and goals
Migration `20261108120000_create_households_and_goals.sql`: `households`, `household_members`, `share_grants`, `goals`, all **service-role-only** with only the privileges current code uses. Do not add policies or client grants.
- `household_ensure_for_user` (wrapped by `ensureHouseholdForUser`, `householdEnsure.ts`) returns or creates the user's one-person household under a per-user advisory lock; there is no backfill, so a route that reads households should call it first.
- A goal is personal or joint, never both; amounts are integer cents. That file gives `share_grants.resource_id` no foreign key; the share file below adds one.
- Deleting a user cascades to memberships, the share grants and answers the user gave or received (where the share file is applied), and personal goals; `household_delete_if_no_active_members` then deletes emptied households. That trigger function must stay SECURITY DEFINER, owned by the owner of `households`, or account deletion fails with 42501.

**Invites, joining and leaving** (migration `20261120120000_household_invites_and_membership_changes.sql`; whether it is applied is live state, and the household routes and the account export must not be deployed against a database without it).
- That file adds `household_invites` (one open invite per household; the invitee's trimmed, lowercased address and the token's SHA-256 only, never the token) and `household_invite_issues` (per-user creation count), both service-role-only, and grants service_role UPDATE on `household_members` **on `status`, `left_at` and `role` only**; `user_id` and `household_id` stay unwritable. It adds no trigger and no SECURITY DEFINER function.
- **Every membership or invite write goes through a SECURITY INVOKER function**: that file's, `household_ensure_for_user` for the one-person membership, and `household_leave` as the share file below redefines it; the routes never write those tables directly. Each function that reads a membership before it writes takes the caller's user lock (the same key as `household_ensure_for_user`), then the lock of each household it changes (ascending id when two), and decides only on what it reads after both; the single-statement issue counter and expired-invite prune take no lock. Keep that order in any new function, or it can deadlock with the existing ones.
- The member limit is two, held both by `household_max_members()` in SQL and by `HOUSEHOLD_MAX_MEMBERS` (`householdInvite.ts`); a test holds them equal.
- **Owner succession.** Leaving as the owner promotes the earliest-joined remaining member inside `household_leave`. Account deletion does not: deleting the owner's account leaves the other person a `member` of a household with no owner until `household_repair_owner` runs, which `GET /api/household` and invite creation call. The dashboard's household card calls that GET on every dashboard visit, so opening the dashboard runs `household_ensure_for_user` and can promote the remaining member. A household emptied by two simultaneous deletions can be left with no active member; that is accepted.
- **Expired invites.** No answer depends on whether an expired invite has been deleted: the view's read, preview and `household_invite_accept` each compare `expires_at` with the current time themselves. Expired rows are deleted by `GET /api/cron/prune-household-invites` (hourly in `vercel.json`; the cron bearer check, 503 without the service-role key, 500 when the call fails, logged as `[household-prune]`), and by `household_invite_create` as a side effect; `GET /api/household` deletes none. A cron run that fails or does not happen only keeps expired rows, and so exports them, longer.
- **Running `20261108120000_…` again after the invites file silently removes the column UPDATE** (its DO block still passes); the invites file's DO block detects it, and applying that file again restores it.
- Routes live under `src/app/api/household/`; each handler starts with `householdGate` (`householdRoute.ts`: 503 `ADMIN_UNCONFIGURED` before auth; then `resolveRequestAuth`, where an unreachable auth server is 503 `AUTH_UNAVAILABLE` and every other cause 401), and identity, email and email-confirmed state come only from the verified token. Preview and accept answer 403 `EMAIL_UNCONFIRMED` before any read when the caller's address is not confirmed, and one identical 404 `INVITE_UNAVAILABLE` whenever the token does not lead to an open invite for that address, compared after trim and lowercase. Log lines carry route, outcome and an error code only. The shared-accounts route's own lines add counts, or the crypto module's reason when an owner's read throws; the bank reads it makes in the same request also write the bank adapter's `[bank-read]` and `[bank-contract]` lines, which end in `origin=household-shared` and carry status, error code or crypto reason, and counts.
- The invite link carries the token in the URL **fragment** under `household_invite` (not a key auth-js or `/auth/callback` reads). The accept page (`/settings/household/accept`) moves it to memory, removes the fragment, and accepts only on a button press; nothing is written to browser storage. The middleware sends a signed-out visitor to a bare `/login`, so they must open the link again after signing in.
- **Dashboard household card** (`src/app/dashboard/HouseholdCard.tsx`, decisions in `householdClient.ts`): reads `GET /api/household`, holds its own state and takes no props, so it does not hold up the other cards. Its session read and request end at `HOUSEHOLD_CARD_FETCH_TIMEOUT_MS`; anything but a well-formed 2xx shows it as unavailable, never as a one-person household. The card file itself formats no amount (`dashboardHouseholdCard.test.ts` holds that), writes no browser storage and never signs out. When the household has two people it mounts `SharePrompt` (below) and `SharedAccounts` (below), each of which makes its own request.

**Sharing a bank connection** (migration `20261121120000_household_share_grants.sql`; whether it is applied is live state, and the sharing route and the account export must not be deployed against a database without it).
- A `share_grants` row means the owner lets one person (`grantee_user_id`) see one of their bank connections. Turning sharing off deletes the row, so a row exists exactly while the connection is shared; `revoked_at` stays null. `(owner_user_id, resource_id)` references `plaid_connections (user_id, id)` on delete cascade, so every path that deletes a connection row, and deleting either person's account, removes the grant. `share_prompt_answers` (primary key `id`, unique `(resource_id, grantee_user_id)`, the same foreign keys) records that the owner was asked about a connection for a person; it records no answer, and a new partner is asked again. Both tables are service-role-only; service_role holds SELECT, INSERT and DELETE and no UPDATE.
- `household_share_set` (SECURITY INVOKER, user lock then household lock) is the only function that inserts into either table. It finds the connection by the caller's id and the item id, and answers `solo` unless the household has exactly one other active member. `household_leave`, as that file redefines it, also deletes the grants and answers the leaving person gave or received in that household.
- **Running an earlier file again undoes part of it.** `20261108120000_…` takes back service_role INSERT and DELETE on `share_grants`, so until the share file is applied again every call of `household_leave` or `household_share_set` that reaches its delete from `share_grants` fails with a permission error (42501) and answers 500: leaving a household that has another member, and changing sharing of a connection by someone with exactly one other member. Calls the functions answer before that delete (leaving alone, no household, no other member, no such connection) are not affected; `20261120120000_…` restores a `household_leave` that deletes no share rows. Apply the share file again after either: it deletes every grant and answer whose owner or grantee is not an active member of the row's household, and its DO block detects both. A person who left in that window and has since rejoined the same household keeps the old rows. Reversing `20261107130000_…` needs the share file reversed first.
- **When a grant is deleted, by any path** (turning sharing off, leaving, a deleted connection, a deleted account, a deleted household), the trigger `trg_share_grants_purge_chat` of migration `20261122120000_chat_shared_sources.sql` (whether it is applied is live state) deletes, for every session of the grantee marked with that owner and connection, the messages created at or after the recorded moment and the mark itself, and lowers the session's `message_count` by the number deleted. The session, its earlier messages, `last_message_at`, and summaries and facts that already exist are kept. Its function is SECURITY DEFINER with an empty search_path and must stay owned by the owner of `chat_messages`, `chat_sessions` and `chat_shared_sources`, or its deletes match no row without an error; no role holds EXECUTE on it. `chat_shared_sources` is service-role-only: service_role holds SELECT, INSERT and UPDATE on `first_shared_at` only, and the only function that inserts is `chat_shared_turn_save` where migration `20261124120000_chat_shared_turn_save.sql` is applied, `chat_shared_source_record` where only the earlier file is (whether each is applied is live state); both are SECURITY INVOKER. Its owner and connection columns carry no foreign key on purpose: a cascading one would remove the row before the trigger reads it. The purge function and the inserting function take the same advisory lock, keyed by resource type, owner and connection, and no household lock. `TRUNCATE` on `share_grants`, a disabled trigger and `session_replication_role = replica` do not fire it; that file, applied again, removes what a mark without a grant left.
- **What the purge changes elsewhere.** A purged span disappears from the chat screen on its next load and from the next turn's history; a crisis signal in it no longer counts as an earlier signal, so a later one gets the first notice, not the escalated one. A turn saved just before a purge can answer 500 `SAVE_FAILED`, because the lookup no longer finds it.
- **Order between the share file and the chat shared sources file.** The share file's closing check accepts `share_grants` with no user trigger or with exactly that purge trigger, enabled and as defined, so it can be applied before or after the other; `share_prompt_answers` accepts none. Reverse the chat shared sources file before the share file: the share file's reverse drops `grantee_user_id`, which the purge function reads, and every later delete from `share_grants` would fail.
- **Reading what another member shares.** Migration `20261123120000_household_shared_connections.sql` defines `household_shared_connections(p_user_id)` (whether it is applied is live state, and the shared-accounts route must not be deployed against a database without it: every call then answers 500). It returns a connection row only when, in one statement, an open `view` grant of a `plaid_connection` names `p_user_id` as grantee, the owner is someone else, both are active members of the grant's own `household_id`, and the connection row is the owner's and `active`; `household_id` alone decides nothing. It is STABLE and SECURITY INVOKER with an empty search_path, and only service_role holds EXECUTE. Any new reader of another member's data goes through it rather than naming the share tables.
- **`GET /api/household/shared-accounts`** (`householdSharedAccounts.ts`, store `householdSharedAccountsStore.ts`) starts with `householdGate` and calls the function with the verified caller's id only. It reads each owner's connections in a separate `readBankData` call, accounts only with no Item read and no engine, with that owner's id; reads not finished after `SHARED_ACCOUNTS_READ_TIMEOUT_MS` are cancelled. It then calls the function again and answers only the connections still returned, keyed by owner and connection id, so sharing that ended during the read is not shown; the owners' first names are read after that check, so sharing that ends during that one read, or after the answer, stays on screen until the next load. Each account's descriptive fields are put in the shape the screen's reader requires: a name or type that is not a string is answered as an empty string, a mask or subtype that is not a string as null, and a currency code that is not a string or is blank as null. The amounts are not changed: one that is not a whole number of cents makes the screen distrust the whole answer. It writes nothing. A failed call of the function is 500, never an empty list. `HOUSEHOLD_SHARED_ACCOUNTS_MODE` exactly `off` answers an empty list with nothing read.

### Account safeguards
**Reauthentication before account deletion and export** (`src/lib/accountReauth.ts`, wiring in `accountReauthRoute.ts`).
- What it stops: a stolen session or token deleting the account or downloading its data. It does not stop someone who also holds the user's mailbox.
- `POST /api/account/reauth/start` emails a one-time code for one purpose (`delete_account` or `export_data`) to the address on the verified token, only when the auth server reports that address confirmed (409 `REAUTH_EMAIL_UNAVAILABLE` otherwise), after the code's row is stored; `POST /api/account/reauth/verify` checks a typed code. Neither reads an address or a user id from the body.
- `POST /api/account/delete` and `GET /api/account/export` call `requireRecentReauth` right after authentication and before anything else: 403 `REAUTH_REQUIRED` without a recent verification for their purpose made by the request's own sign-in session, 503 `REAUTH_CHECK_UNAVAILABLE` when the check cannot be made. The session is the `session_id` claim of the bearer token the auth server has just accepted, read from that same string (`sessionIdFromVerifiedToken`); a token without one gets 403 `REAUTH_SESSION_UNAVAILABLE` from start, from verify and from the gate (one decision, `requireSession`), before any rpc or email, and a verification made in one session does not answer for another. The export check uses the verification up; the delete check only reads it, since a deletion that stops part-way is retried. What the browser was told about a code decides nothing.
- `ACCOUNT_REAUTH_MODE` is exact-match: only `off` skips all of this; unset, empty and every other value enforce.
- The database decides, through the functions of migration `20261121130000_account_reauth_codes.sql` (whether it is applied is live state); under enforcement every check fails closed, so that file must be applied before this code is deployed against a database. Limits, lifetimes and windows are application constants passed as arguments. Its rows reference `auth.users`, so a retry after a deletion that removed the `users` row but not the Auth user still finds its verification.
- Only a keyed hash of a code is stored: an HMAC under a key derived (HKDF) from `SUPABASE_SERVICE_ROLE_KEY` with the label `noor/account-reauth-code/hmac-sha256/v1`, so a copy of the table alone does not give the codes back. Without that key no code is issued or checked. The code, the key, the hash and the address never reach a log line or a response.

**Signing out other devices**: `POST /api/account/sessions/sign-out-others` (`accountSessions.ts`) signs out every other session of the token's user, with the admin sign-out and scope `others`; another device is signed out when its session next refreshes, not at once, and nothing on this device is cleared. Whether the auth server keeps the requesting session itself is checked on a preview deployment, not in tests.

## Models / OpenRouter
- **Live model configuration is env-driven and not recorded here.** In-code default constants are overridden by their env vars. The chat route has a primary and a fallback model on different lines (model, not provider, redundancy). The simple/complex split is skipped when `OPENROUTER_MODEL` is set, so group cost by the `model` column.
- **OpenRouter is the only provider path**; without `OPENROUTER_API_KEY` chat answers 503.
- **Every request carries routing preferences** (`src/lib/openRouterRequest.ts`): zero-data-retention, data-collecting providers denied, US-only endpoints. With no passing endpoint the call fails; the fix is pinning a model id with one in the model env vars, then redeploying.
- **Timeouts and budgets** live in `src/lib/llmTimeouts.ts`: per-attempt timeouts, a request budget, a pre-loop deadline and a save deadline; the chat route answers 503 `CHAT_TIME_BUDGET_EXHAUSTED` when time runs out before any model attempt starts. Values are unvalidated defaults.
- **Every started attempt failing gives one 502 `CHAT_MODEL_FAILED`**; no upstream status or text reaches the client. A provider 401 skips the fallback. Each failed attempt logs one `[chat-model]` line, a successful one none; read attempts one by one in `llm_calls` before assuming which model failed.
- **OpenRouter conventions:** `~` is required for `latest` aliases; pinned versions use dots, no tilde. Never guess a model ID. Model retirement is silent.
- **Parsers must absorb model output drift** (code fences, missing or renamed fields, extra text): skip and log, never crash or misstore.

## Security principles
- **Authentication ≠ authorization.** Past holes were "logged in but no permission check" or "trusted a client value." **Access control lives in service-role-only tables** (`admin_users`); never put admin flags on user-accessible tables.
- **UI hiding is not a security boundary; the API is** — but pages still need their own gate.
- **Client `userContext` and history are discarded** in `/api/chat`. Names go through `sanitizeNameField`; never reintroduce an ASCII-only name check.
- **Dead tables are live risk**; prefer dropping them. **RLS is meant to be on for every table**; actual RLS and policies are live state (`pg_policies`). The chat memory tables are meant to be written through the service-role client only.
- Where `20261107140000_close_default_privileges_for_client_roles.sql` is applied, new objects postgres creates start closed to client roles; a migration still grants what it needs explicitly and asserts the end state.
- **Verify that a threat vector exists before investing in the defense.** **Blast radius sets severity**: own data vs another user's.
- **`localStorage` is not a source of truth**; client guards keyed on it are display logic. Terms acceptance is recorded in localStorage only — do not describe consent as recorded server-side.
- **A silent failure is worse than an explicit error**; never report success on an unverified side effect. **Fire-and-forget means never sent** on Vercel: await side effects; email failure must not block the primary action.
- **Collect the minimum**; columns written and never read are collection without a purpose.

## Strategic decisions (so they aren't re-litigated)
- Do not gate launch on Plaid or legal answers; keep a fallback path that ships without them. Build defensively under legal uncertainty.
- A rebuilt recommendation engine stays rules-based; AI does input extraction and understanding only. AI advice quality is prompt-level work and the core differentiator; the remaining work is the reasoning scaffold.

## Gotchas
- **Never read `package-lock.json` whole**; grep it.
- **`docs/` is stale and not a source of truth.** Read the code; ask the operator about past decisions.
- **A rolling usage window doesn't clear on redeploy**; switch the mode to stop refusals. **No migration here backfills**; populating existing rows is a separate manual step.
- **SMTP password = the `hello@noor.financial` mailbox password**; if reset, update Vercel and Supabase Custom SMTP. **The repo is at `C:\dev\noor`, outside OneDrive.** Impossible file behavior usually means another process holds the file.
- **`auth.uid()` against a `TEXT` column needs `auth.uid()::text`.** `plaid_connections.user_id` may be `TEXT` or uuid depending on whether `20261107130000_…` is applied; read the live type.
- **OAuth provider state and signup blocking are live configuration** at two independent layers (Supabase toggle for OAuth, `SIGNUP_DISABLED` for email). Verify both.
- **Git author, commit messages and branch names are weak evidence**; read the diff. **Soft wrap looks like a syntax error** in terminal and diff output; `cat` the file when in doubt.
- **Adding a feature can wake dormant configuration.** Re-review corrected code.
- **Grep here:** Git-for-Windows grep aborts on `-i` with multiple `-e` patterns (use `-E 'a|b'`); a `printf` format starting with `-` is an option; Git Bash `grep` strips CR unless `-U`.
- **Fintech SEO is YMYL**; don't serve the same content on two hosts.
